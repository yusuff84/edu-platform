## Подтверждённые проблемы по коду

Ниже приведены условия воспроизведения, выведенные из кода. Они не обозначают выполненную браузерную или платёжную эксплуатацию.

### R01 · P0 · Платный контент доступен гостю

Источник: `backend/internal/handler/courses.go:188`, `:225`.

`GET /api/v1/courses/{slug}` для published-курса не проверяет enrollment. `lessonToView` всегда включает bodyMd, videoUrl, liveUrl, startsAt; full=false скрывает правильные ответы и hidden-тесты, но не содержимое платного урока. Гость получает материалы всех уроков независимо от isPreview. Отдельный preview endpoint эту утечку не предотвращает.

- [ ] Разделить публичную программу курса и содержимое уроков. Контент выдавать владельцу, админу, активному покупателю или для разрешённого превью.
- [ ] Регрессия: гость и пользователь без покупки не получают текст, видео и ссылку эфира обычного платного урока; покупатель получает; preview продолжает работать.

### R02 · P0 · Учебный код имеет сетевой доступ к API и общую среду с runner

Источники: `runner/main.go:171`, `runner/Dockerfile`, `docker-compose.yml`.

Все решения выполняются от одного UID внутри долгоживущего контейнера. Runner и API состоят в runner_net: internal=true закрывает внешний интернет, но не доступ к API в этой сети. Python/Node-код может обращаться к API и другим проверкам, видеть доступные тому же UID файлы и посылать сигналы процессам. Ограничения контейнера полезны, но не изолируют исполнения друг от друга и от управляющего сервиса.

- [ ] Изолировать каждую проверку отдельной песочницей с отдельными PID/FS и запрещённой сетью. Управляющий runner должен находиться вне среды выполнения ученического кода.
- [ ] Проверить невозможность доступа к API, файлам соседней проверки и управляющему процессу. Выполнять проверки на отдельном тестовом стенде.

### R03 · P1 · Таймаут runner не завершает дерево процессов

Источник: `runner/main.go:171–184`.

CommandContext убивает непосредственный процесс, но процесс-группа/дерево не управляются, WaitDelay не задан. Дочерний процесс может пережить родителя; если удерживает stdout/stderr, cmd.Run продолжает ждать pipe после дедлайна. Запрос сохраняет слот семафора; четыре таких запуска могут исчерпать весь runner. read/write timeout HTTP не очищает дерево процессов.

- [ ] Завершать всю песочницу по дедлайну и при отмене запроса; ограничить ожидание pipe.
- [ ] Linux-регрессия: код порождает дочерний процесс, родитель завершается/убивается; ответ и освобождение слота укладываются в бюджет, дочерних процессов не остаётся.

### R04 · P1 · Повторная покупка Stripe/YooKassa возвращает пустую ссылку

Источники: `backend/internal/handler/enroll.go:73`, `backend/internal/payments/provider.go:143`, `frontend/src/pages/Course.tsx:100`.

При pending-платеже POST /enrollments возвращает ResumeURL; для реальных провайдеров это пустая строка. UI ничего не делает, если нет redirectUrl и enrollmentActive=false. После закрытия страницы оплаты пользователь не может возобновить покупку. Комментарий «фронтенд создаёт новый платёж» не соответствует реализации.

- [ ] Сохранять redirectUrl/идентификатор checkout-сессии либо восстанавливать ссылку через адаптер. Определить обработку истёкшей сессии.
- [ ] Повтор покупки и повтор после рестарта API возвращают рабочую ссылку либо явно создают новую сессию по принятой политике.

### R05 · P1 · Платёж создаётся до локальной записи, конкурентные покупки не сериализованы

Источник: `backend/internal/handler/enroll.go:73`, `:156–169`.

Проверка pending и создание не атомарны. Два параллельных запроса могут оба не найти pending и создать два внешних платежа. PaymentID генерируется случайно при каждом запросе, поэтому провайдер не объединит повторы. Если провайдер уже создал платёж, а запись БД не удалась, внешний платёж останется без локального следа.

- [ ] Ввести долговечную попытку покупки до сетевого запроса, стабильный ключ идемпотентности и ограничение конкурентных активных попыток.
- [ ] Добавить сверку зависших платежей и восстановление после таймаута/сбоя записи.
- [ ] Проверки: два одновременных POST, обрыв после ответа провайдера, повтор после рестарта.

### R06 · P1 · Повторный старый вебхук меняет актуальный доступ

Источник: `backend/internal/handler/enroll.go:296`, `:336`, `:371`.

Duplicate succeeded вызывает EnsureEnrollment и снова открывает доступ. Поэтому повтор события после административного отзыва может отменить блокировку enrollment. Duplicate refunded безусловно отзывает доступ по studentId/courseId: после возврата платежа A и новой покупки B повтор refund A заблокирует доступ, оплаченный B. Текущий enrollment не связан с основанием выдачи доступа.

- [ ] Отделить ручной отзыв от финансового статуса и учитывать действующие платежи/актуальный entitlement.
- [ ] Регрессии: succeeded → ручной revoke → повтор succeeded; refund A → покупка B → повтор refund A. Текущее право доступа сохраняет правильное состояние.

### R07 · P1 · Частично выполненный административный возврат нельзя восстановить повтором

Источник: `backend/internal/handler/admin_payments.go:333–385`.

Сначала выполняется внешний Refund, затем сохраняется PaymentRefunded, затем отзывается доступ. Если последний шаг падает, API отвечает 500, но следующий запрос отклоняется на проверке p.Status != succeeded с 409. Комментарий обещает восстановление повтором, однако соответствующей ветки нет. Сетевой вызов также находится до mutex: параллельные запросы могут оба обратиться к провайдеру.

- [ ] Сделать возврат восстанавливаемой операцией со стабильным ключом; повтор должен завершать локальные действия без повторного списания/возврата.
- [ ] Изменять платёж и доступ согласованно; протестировать сбой каждого шага и параллельные запросы.

### R08 · P1 · Успешное завершение урока возвращается при ошибке записи прогресса

Источники: `backend/internal/repo/postgres_store.go:912`, `backend/internal/handler/progress.go:116`.

В SQL-ветке UPDATE игнорирует ошибку; INSERT логирует её и всё равно возвращает объект. Handler не проверяет результат CompleteLesson и отвечает passed=true/completed=true. После обновления страницы завершение может исчезнуть; выдача сертификата также может не состояться.

- [ ] Пробросить ошибку через StoreAPI и handler; не возвращать completed=true до подтверждённой записи.
- [ ] Проверить сбой INSERT/UPDATE и успешное повторное завершение без потери прогресса.

### R09 · P1 · Архивация/снятие с публикации ломает обучение купленного курса

Источники: `backend/internal/handler/courses.go:225`, `frontend/src/pages/Learn.tsx:74–84`.

MyCourses сохраняет активную покупку, но Learn загружает содержимое через публичный GetCourse. Для любого непublished-курса GetCourse разрешает чтение только владельцу/админу, даже при активной покупке. Ученик видит курс в кабинете, но получает 404 при продолжении обучения.

- [ ] Разделить доступность продаж и доступность уже купленных материалов; явно определить политику archive/unpublish.
- [ ] Покупатель продолжает обучение после снятия курса с продаж; гость купить его не может.

### R10 · P1 · Лимит использований промокода можно превысить

Источники: `backend/internal/handler/promo_codes.go:234`, `backend/internal/handler/enroll.go:302–315`, `backend/internal/repo/postgres_store.go:1779`.

Лимит проверяется перед созданием оплаты, а used_count увеличивается только после успеха. Несколько pending-платежей получают последнее доступное использование одновременно. UPDATE не ограничивает max_uses, а ошибку увеличения счётчика обработчик только логирует. Даже один экземпляр API не обеспечивает лимит.

- [ ] Ввести атомарное резервирование использования и освобождение резерва при отмене/истечении оплаты; закрепить правила для позднего успеха.
- [ ] При maxUses=1 две конкурентные покупки не получают две подтверждённые скидки; повтор вебхука не увеличивает счётчик дважды.

### R11 · P2 · Приватный React Query-кэш переживает смену аккаунта

Источники: `frontend/src/app/router.tsx:95`, `frontend/src/pages/Auth.tsx`, `frontend/src/pages/Profile.tsx:50`, `frontend/src/pages/Learn.tsx:74`.

Logout сбрасывает только ['me']; login/register также инвалидируют только ['me']. Остальные ключи не включают userId: my-courses, me-profile, me-payments, favorites, course-progress и learn-course. При входе другим аккаунтом старые данные остаются в памяти и могут отображаться до завершения refetch, в том числе при его ошибке.

- [ ] Очищать приватные queries при смене сессии и/или включить идентификатор пользователя в их ключи; отменять старые запросы.
- [ ] Браузерный тест A → logout → B при медленной/ошибочной сети: данные A не появляются.

### R12 · P2 · Клиент выбирает язык проверки задания

req.Language имеет приоритет над l.CodeTask.Language; CheckCode проверяет только принадлежность общему списку python/js/htmlcss. Ученик может отправить решение другого языка и обойти выбранный автором режим проверки, включая переключение с запуска программы на статический HTML/CSS-checker.

- [ ] Брать язык из задания либо проверять совпадение с явно разрешённым набором языков задания.
- [ ] Отправка htmlcss/js для Python-задания отклоняется до обращения к runner.
