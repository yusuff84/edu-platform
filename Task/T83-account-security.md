# T83 — сброс пароля, подтверждение email и управление сессиями

Реализованы три пользовательских сценария:

- На странице входа есть «Забыли пароль?». По email отправляется одноразовая
  ссылка на `/reset-password#token=...`; форма требует новый пароль и повтор.
  После успешного сброса все сессии аккаунта отзываются, автоматического входа нет.
- При регистрации с настроенной почтой отправляется подтверждение. В профиле
  показан статус адреса и есть повторная отправка. Ссылка `/verify-email#token=...`
  требует отдельного нажатия кнопки: чтение письма и GET не подтверждают адрес.
  Неподтверждённый email не блокирует существующий доступ к платформе.
- В профиле отображаются активные сессии: браузер/ОС, IP, время входа, последняя
  активность, истечение и текущая сессия. Можно завершить одну, все другие или
  текущую. Чужие сессии нельзя просмотреть/отозвать.

## Хранение и ограничения

Миграция `017_account_security.sql` добавляет `users.email_verified_at`, metadata
сессий и таблицу `account_tokens`. Пользователи и существующие сессии сохраняются;
старыми сессиями тоже можно управлять. `emailVerified` добавлен в auth-response.

Токен содержит 256 случайных бит; БД хранит только SHA256. Для пользователя
действует одна ссылка каждого назначения, новая заменяет предыдущую. Сброс
действует 30 минут, подтверждение — 24 часа. Повторная отправка ограничена одной
минутой на аккаунт и IP-лимитом recovery/verification endpoints. Сброс удаляет
все токены и сессии аккаунта одной транзакцией. Создание сессии проверяет тот же
хеш пароля, который прошёл проверку входа: вход со старым паролем не переживает
параллельный сброс.

Список сессий возвращает отдельный management UUID, а не cookie credential.
Metadata берутся из запроса и служат подсказкой владельцу; это не удостоверение
устройства. Активность обновляется примерно раз в 5 минут.

Forgot-password возвращает одинаковый 202 для существующего, отсутствующего,
заблокированного и временно ограниченного аккаунта. Отправка писем выполняется
вне HTTP-запроса с ограниченной конкурентностью. Ошибка доставки удаляет токен,
чтобы можно было повторить запрос. Задачи доставки находятся в памяти: после
перезапуска до отправки пользователь может повторно запросить письмо через
минуту. Секретные ссылки в API и журнал не выводятся. Фрагмент удаляется из
адресной строки после чтения формой; для повторного открытия нужна ссылка из
письма. Пароль: минимум 8 символов, максимум 72 UTF-8 байта (bcrypt).

## Настройка писем

Для реальной доставки нужны существующие SMTP-настройки и корректный
`PUBLIC_APP_URL`. В production адрес приложения должен быть HTTPS без userinfo,
query и fragment. Без SMTP функции писем возвращают 503 с понятным сообщением;
профиль не обещает отправку и показывает недоступность почты. Подтверждение
уже выпущенного токена и сброс по нему не требуют доступного SMTP.

Локальная проверка без внешней почты:

```powershell
docker compose -f docker-compose.yml -f docker-compose.dev-mail.yml up -d --build
```

Только в dev: override подключает SMTP-приёмник и просмотр тестовых писем на
`http://127.0.0.1:13025`. Письма не доставляются внешним адресатам. Не подключать
этот override к production; SMTP_TLS=none в production запрещён.

## Проверки

- Контрактные тесты: реальное потребление ссылок из перехваченных писем,
  одинаковые recovery-ответы, cooldown, wrong purpose, expiry, blocked account,
  параллельное потребление, отзыв сессий, ownership и отказ хранилища.
- PostgreSQL: parity с memory Store, атомарный откат пароля при сбое удаления
  сессий, гонка reset/login, одноразовость, старые сессии.
- Chromium E2E через локальный SMTP: подтверждение и повтор ссылки, сброс с
  проверкой нового/старого пароля и отключением другого устройства, управление
  сессиями из профиля. Остальные 5 браузерных сценариев сохранены.

Результат приёмки 17.11.2026: полный `go test -count=1 ./...` с PostgreSQL и
`go vet ./...` прошли; account contract-тесты дополнительно прошли с `-race`
в Linux-контейнере. Frontend build и 193 contract-теста прошли. Все 8 Chromium
E2E прошли локально и на Docker/PostgreSQL/nginx с локальным SMTP, включая
мобильный профиль. Внешний SMTP-провайдер этим не проверяется.
