# Эксплуатация и приёмка

## Проверки перед выпуском

Релиз проверяется на точном commit с PostgreSQL, а не только на memory Store:

```powershell
cd backend
$env:TEST_DATABASE_URL = 'postgres://user:password@127.0.0.1:5432/edu_test?sslmode=disable'
go vet ./...
go test -count=1 ./...
cd ../frontend
npm ci
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

Playwright самостоятельно поднимает отдельный API на 18082 с memory Store,
Vite на 13000 и локальный SMTP-приёмник на 11025 с просмотром писем на 13025.
Это проверка браузерных потоков; SQL проверяется отдельным Go-набором. Порты
должны быть свободны. Тесты не подключаются к production-БД и не отправляют
письма внешним адресатам.

Для отдельного тестового Compose-стенда можно задать `E2E_BASE_URL` перед
`npm run test:e2e`: встроенные серверы тогда не запускаются. На стенде должны
быть bootstrap-учётки `admin@e2e.test` и `teacher@e2e.test` с паролем
`e2e-password123`, dev mock-провайдер и разрешённый Origin стенда. Это только
тестовые данные; не использовать такой конфиг для production.
`PUBLIC_APP_URL` должен совпадать с Origin стенда, чтобы ссылки приглашений
вели на работающий frontend.
Для T83 на внешнем тестовом стенде подключить `docker-compose.dev-mail.yml`
и задать `E2E_MAIL_URL` (по умолчанию `http://127.0.0.1:13025`). Это локальная
тестовая почта; не использовать override и тестовые адреса в production.

На Linux выполнить `cd runner && RUNNER_REQUIRE_SANDBOX_TEST=1 go test -count=1 ./...`. Нужны Python, Node и bubblewrap, разрешённые unprivileged user namespaces. Обязательный тест проверяет сокрытие файлов хоста, отдельный PID namespace и отсутствие внешней сети. Без работающей изоляции runner не стартует; автоматического перехода на выполнение без sandbox нет.

`RUNNER_SANDBOX=none` предназначен исключительно для явного локального запуска. Compose использует bubblewrap. Внешний контейнер ограничивает общую память/CPU/PID, а bubblewrap изолирует отдельные исполнения. Вложенные namespaces требуют разрешения на хосте; Docker Desktop/WSL и AppArmor могут запрещать их. Не отключать sandbox ради зелёного healthcheck. Настроить политику хоста и подтвердить `TestSandboxIsolation` до использования ученического кода.

API-порт Compose привязан к 127.0.0.1. Публичный трафик направляется через HTTPS reverse proxy. `TRUSTED_PROXY_CIDRS` задаётся фактическими адресами доверенных прокси; пустое значение не доверяет заголовкам IP даже от private/loopback узлов. Для Docker нужно указать адрес/выделенную подсеть web-прокси. Не включать в список сети, из которых клиенты могут обращаться к API напрямую.

## Резервная копия и восстановление

Нужны PostgreSQL client tools в PATH. Пароли хранить в переменных окружения/секретах, не в скриптах или manifest. Версия pg_dump должна быть совместима с сервером. Для согласованной копии БД и обложек на время копирования остановить изменения данных или использовать согласованный snapshot хранилищ.

```powershell
./scripts/backup.ps1 -DatabaseUrl $env:DATABASE_URL -Destination C:/backups/edu-2026-11-17 -UploadsPath C:/edu/uploads
./scripts/restore.ps1 -DatabaseUrl $env:RESTORE_DATABASE_URL -BackupPath C:/backups/edu-2026-11-17 -UploadsPath C:/edu-restore/uploads
```

Backup сохраняет custom-format dump, архив uploads и SHA256 manifest. Restore проверяет хеши и отказывается писать в непустую БД/каталог. БД восстанавливается одной транзакцией. Не переключать рабочий трафик до проверки БД, доступа к курсам и изображений. Если извлечение uploads прервалось после восстановления БД, БД уже восстановлена: не запускать restore повторно в ту же БД, завершить восстановление файлов отдельно.

Назначить владельца резервирования, периодичность и срок хранения; хранить копии вне хоста приложения с контролем доступа. Регулярно восстанавливать копию на отдельном стенде и фиксировать время восстановления. Подготовленные скрипты не означают, что production-расписание и внешнее хранилище уже настроены.

## Наблюдение и сбои

- Проверять `/healthz` и состояние контейнеров; отдельно контролировать соединение PostgreSQL и сохранность volume uploads.
- Собирать stdout/stderr API и runner в систему журналов. Оповещать о серии 5xx в покупке/вебхуках/возвратах, ошибках PostgreSQL, недоступном runner и росте pending-платежей.
- При сбое провайдера повтор покупки использует сохранённый payment ID и исходные параметры. Не создавать вручную новый внешний платёж для той же попытки после неопределённого сетевого результата.
- Старые pending-записи без сохранённой ссылки возвращают явную ошибку. Для ручной сверки: `POST /api/v1/admin/payments/{id}/sync` с admin-cookie и разрешённым Origin. Незавершённый checkout восстанавливается по исходному ключу, затем статус сверяется с провайдером. Срок хранения ключей идемпотентности ограничивается провайдером: старые неопределённые попытки сначала проверять в его кабинете. Текущая версия не содержит фоновой автоматической реконсиляции.
- Промокод резервируется попыткой оплаты. Неопределённые/failed попытки сохраняют резерв, поскольку возможен поздний успех; автоматическое освобождение требует подтверждения необратимой отмены у провайдера. Это сознательное ограничение против превышения maxUses.
- Проверить старые production-БД на демо-аккаунты прежних версий. Не удалять пользователей или платежи без проверки связей и резервной копии.

## Внешняя приёмка

Ключи Stripe/YooKassa, живой SMTP, OAuth-приложение, публичный HTTPS-домен, CI в GitHub и инфраструктура резервирования требуют соответствующего окружения. Зафиксировать реальные результаты: покупка/отмена/повтор/вебхук/возврат, приглашение с доставкой письма, OAuth callback, зелёные jobs и успешное восстановление. Локальные моки не заменяют эти проверки.

Несколько API используют общий PostgreSQL advisory lock для платёжных операций; применение статуса, счётчика промокода и доступа атомарно. Глобальная блокировка ограничивает пропускную способность: перед масштабированием измерить нагрузку и перейти к более узким блокировкам. Rate-limit остаётся process-local; uploads требуют общего volume/объектного хранилища. Настройки комиссии и баннера уже читаются из PostgreSQL при запросе — отдельной проблемы репликации их кэша в штатном режиме нет.
